    Шаги

    1. План и каркас (этот PR)

    README (включая примечание о вышестоящем smart-trust-phw), AGENTS.md, этот план, предложение по платформе приложения, директивы владельца в memory/, реестр зависимостей и задание CI, которое проверяет, что каждый GitHub Action закреплён по SHA коммита и каждый JSON-файл разбирается.

    2. Пути как содержимое cat-harness

    • (выполнено) Декларация smart-trust-demo.json и index.config.json, закрепляющий слои обвязки, которые закрепляет smart-trust-tools (fhir-harness и ниже), а также сам smart-trust-tools, чтобы идентификаторы req: разрешались; index.lock.json.
    • scenarios/: акторы (с повторным использованием VHL Holder, Sharer, Receiver, Trust Network Participant из smart-trust-tools), роли, исполняющие дорожки, и персоны: мать и новорождённый (пример IG для J1), медсестра клиники J1, CHW (J2), поставщик услуг клиники по месту жительства (J3), национальный портал и получатель на границе/в клинике за рубежом (J4).
    • processes/content/: по одному BPMN на путь (выполнено на шаге 2a; чек-листы и монтирование обвязки — в 2b) (J1 — выдача, J2 — выявление и направление общинным медицинским работником (CHW), J3 — проверка, импорт и график, J4.0 — выдача VHL на общий телефон, J4.1 — получение VHL в месте оказания помощи); дорожки именуют роли, задачи именуют навыки smart-trust-tools; чек-листы сгенерированы.
    • User scenarios: one per journey, each step tracing to req: nodes (e.g. J2 → STT-VER-011, J3 → STT-VER-001…, J4 → the VHL requirements).
    • Beans для пробелов, обнаруженных по ходу работы (в этом репозитории или с пометкой для вышестоящих smart-trust-tools, smart-trust или smart-trust-phw).

    2c. DAK уровня L2 и FHIR IG уровня L3

    Пути в виде DAK и FHIR IG по руководящим принципам SMART ВОЗ (WHO SMART Guidelines), устроенные как litlfred/smart-immunizations (sushi-config.yaml, ig.ini, DAK в index.config.json (contentTypes.dak), input/). Содержимое L2 генерируется из исходников обвязки с помощью tools/ig-gen/ig_gen.py: роли становятся ActorDefinition, BPMN копируется в input/business-processes/, истории и сценарии становятся страницами. CI проверяет, что сгенерированные файлы актуальны и что SUSHI собирается без ошибок. Затем: опубликовать IG на gh-pages и добавить примеры ресурсов для каждого пути (bean IG-01).

    3. Библиотека HCERT на закреплённом коммите

    lib/hcert/: скрипт и связка Gradle, которые извлекают smart-trust-tools на закреплённом SHA, собирают hcert-api и hcert-core (JVM) собственными Gradle и verification-metadata.xml этого репозитория и копируют jar-файлы в lib/hcert/build/libs/, завершаясь ошибкой, если sha256 jar-файла отличается от записанного в lib/hcert/hcert.lock.json (сборка воспроизводима). Приложение и тесты Android зависят от этих файлов. Обновление библиотеки — это коммит в lock-файле плюс build.py --update.

    4. Тест библиотеки на эмуляторе Android (STT-GEN-004)

    (В работе: android-test/ и .github/workflows/android.yml. Метаданные проверки Gradle записываются на раннере GitHub, поскольку этот сеанс не может связаться с Google Maven.)

    android-test/: модуль библиотеки Android, инструментированные тесты которого выполняются на эмуляторе в CI (уровни Android API предстоит выбрать: один актуальный и один достаточно старый, чтобы иметь значение для клиник, например 26 и 35):

    • проверить пример из §12 IG по DID-документу DSC от XXR (список доверия DEV) с помощью платформенных поставщиков Android;
    • readUnverified того же QR-кода (J2);
    • выдать с ключом Android Keystore (prepare → подпись Keystore → finish) и проверить, ES256 и PS256, если платформа его предоставляет;
    • VHL: собрать и прочитать vhlink:/, расшифровать тестовые данные JWE.

    Результаты передаются в smart-trust-tools как свидетельства для STT-GEN-004 (и как beans там для всего, что отвергает Android, например имён алгоритмов). Артефакты Google Maven (AGP, AndroidX test) закрепляются с sha256, как и все остальные. Задание эмулятора использует действие, закреплённое по SHA, и не кэширует непроверенные артефакты.

    5. Приложение

    (Начато: app/, офлайн-чтение J2 и проверка и импорт DVC из руководства в J3 на Android, рабочий процесс app.yml. Проверенный DVC становится ресурсом FHIR R4 Immunization со своим Provenance (dev.ohs.fhir:fhir-model-r4); непроверенный не импортируется. Далее: график J3, затем выдача J1.)

    На основе, которую владелец выберет из предложения (рекомендуется: компактное приложение Compose Multiplatform на библиотеках OHS KMP, сначала Android):

    • J1: клиника выдаёт DVC новорождённого (встроенный тестовый ключ вместо DSC клиники или Keystore), печатает/показывает QR-код.
    • J2: CHW сканирует бумажный QR-код офлайн (readUnverified), регистрирует младенца (опросник SDC), создаёт направление (ServiceRequest).
    • J3: клиника проверяет по встроенному списку доверия DEV, импортирует Immunization в FHIR-движок на устройстве, оценивает график (PlanDefinition/$apply), показывает следующие дозы.
    • J4: портал выдаёт QR-коды VHL для каждого члена семьи на общий телефон; получатель загружает манифест (ITI-YY5) с локального тестового отправителя (sharer) и расшифровывает.

    UI-тест на эмуляторе проводит четыре пути от начала до конца.

    6. Веб и публикация

    Веб-цель (как только hcert-core заработает в браузере, а тем временем через библиотеку Rust/wasm) и сайт gh-pages (публикуемый агентом): пути, средства просмотра BPMN, персоны и свидетельства тестирования.

    Открытые вопросы

    • Сеть: этот сеанс не может связаться с dl.google.com (Google Maven, Android SDK). Шагам 4–5 это нужно локально для записи метаданных проверки; владелец может разрешить это в сетевых настройках среды.
    • Браузерная сборка hcert-core (для веб-цели): будет поднята в smart-trust-tools.
    • Имена алгоритмов в Android: JVM-код hcert-core запрашивает RSASSA-PSS, который поставщики Android могут не предоставлять под этим именем; шаг 4 покажет.
