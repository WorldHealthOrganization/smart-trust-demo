    Statut : décidé le 2026-10-23 : option B, par étapes, avec entre-temps la bibliothèque Rust/wasm pour le web (memory/dir-app-platform.md). Recherches effectuées le 2026-10-23. Question : sur quelle base construire l’application J1–J4, de sorte qu’elle exécute la bibliothèque Kotlin HCERT sur Android (et, idéalement, sur le web) avec l’Open Health Stack la plus récente et la plus native en Kotlin ?

    1. Ce qu’est Open Health Stack aujourd’hui

    Open Health Stack (OHS) a débuté comme un ensemble de composants mené par Google et est aujourd’hui l’OHS Software Foundation, un projet communautaire relevant de la Linux Foundation, que l’OMS a rejoint en juillet 2026. Son code se trouve sur github.com/ohs-foundation (28 dépôts). Il existe deux générations de bibliothèques client :

    Génération Bibliothèques Plateformes Distribution État
    android-fhir (première) com.google.android.fhir:engine, data-capture (SDC), workflow, knowledge Android uniquement Google Maven « Maintenance » ; dernier commit en février–mars 2026. Workflow exécute du CQL (basé sur HAPI, lourd).
    Kotlin Multiplatform (actuelle) dev.ohs.fhir:fhir-model-r4 1.0.0-rc03, fhir-path-r4, fhir-engine 2.0.0-alpha04, fhir-data-capture 2.0.0-alpha04, fhir-workflow 2.0.0-alpha01; dev.ohs.player:client 1.0.0-alpha03 Android, JVM de bureau, iOS, web (wasmJs, et JS pour certaines) Maven Central Active (commits cette semaine) ; API en alpha. Workflow prend en charge PlanDefinition/$apply ; le CQL est « encore à venir ».

    Au-dessus de la génération KMP se trouve l’OHS Player, décrit par la fondation comme une boîte à outils de référence transversale à la pile, « une référence, pas un produit » :

    • player-reference : le client, une application modèle GitHub en Compose Multiplatform (Android, iOS, bureau, web à partir d’une seule arborescence). Les écrans sont pilotés par la configuration (ViewDefinition SQL-on-FHIR compilés au moment de la compilation), la saisie des données par des questionnaires SDC. Elle s’ouvre sur une connexion OIDC et reste bloquée jusqu’à une première synchronisation avec un serveur FHIR ; il n’existe pas de mode avec données intégrées.
    • player-client : la bibliothèque sous-jacente (vues FHIR pilotées par la configuration), utilisable seule.
    • ohs-player-reference-web-portal : un portail d’administration en TypeScript pour les hiérarchies du personnel (utilisateurs, accès). Ce n’est pas une application web clinique ; sans rapport avec J1–J4.
    • ohs-player-reference-backend, -infrastructure : serveur et déploiement (passerelle FHIR, flux de données).
    • player-reference-examples : variantes de l’application de référence (vide aujourd’hui). Un endroit naturel pour proposer ultérieurement les parcours en amont — un dépôt de l’OHS Foundation, donc uniquement par proposition, jamais depuis ce dépôt.

    Le choix le plus récent et le plus natif en Kotlin est donc la génération KMP, avec ou sans le modèle Player.

    2. Contraintes que toute option doit respecter

    1. Le test sur émulateur Android de la bibliothèque HCERT (STT-GEN-004) doit s’exécuter en intégration continue sur un environnement d’exécution Android, cryptographie de la plateforme comprise. Il est indépendant de l’application : c’est un petit module de test Android qui ne dépend que du jar HCERT (étape 4 du plan). Il peut être livré avant la décision sur l’application.
    2. Démonstration hors ligne et sans serveur. J2 est hors ligne par définition, et l’intégration continue ne peut pas mettre en place à faible coût un fournisseur OIDC et un serveur FHIR pour une exécution sur émulateur. L’application a besoin d’un mode avec données intégrées.
    3. Chaîne d’approvisionnement. Chaque artefact épinglé avec sha256, versions datant d’au moins 14 jours, aucun script d’installation. Moins il y a de dépendances, mieux c’est.
    4. La bibliothèque HCERT provient d’un commit épinglé de smart-trust-tools sous forme de jar JVM (choix du propriétaire). Sur Android, le jar JVM fonctionne tel quel. Sur le web, pas encore : la cible Kotlin/JS de hcert-core utilise node:crypto et node:zlib, elle s’exécute donc sur Node et non dans un navigateur, et il n’existe pas de cible wasmJs. Tout frontal web nécessite soit une cible navigateur dans hcert-core (WebCrypto, CompressionStream), soit une modification de la bibliothèque dans smart-trust-tools, soit la bibliothèque Rust/wasm, qui s’exécute déjà dans le navigateur avec des clés WebCrypto.

    3. Options

    Option A — Dupliquer (fork) l’application de référence OHS Player

    Créer l’application à partir du modèle player-reference ; ajouter un mode de démonstration hors ligne (bundle FHIR intégré, sans connexion), les écrans J1–J4 et les appels HCERT.

    Avantages Inconvénients
    C’est l’OHS Player : le résultat le plus visiblement « OHS », et le plus proche de ce dont partiront les responsables de la mise en œuvre d’OHS. Exige un fournisseur OIDC et un serveur FHIR pour démarrer ; le mode hors ligne est à écrire par nos soins et à fusionner sans cesse avec un modèle qui évolue chaque semaine.
    Android, iOS, bureau et web à partir d’une seule arborescence ; écrans pilotés par la configuration ; les questionnaires SDC pour l’enregistrement (J2) et l’importation (J3) sont déjà intégrés. ~57 bibliothèques et 8 plugins dans son catalogue (Koin, Ktor CIO/Darwin, Kermit, ksafe, kotlinpoet, BigNum, Compose adaptive…), dont plusieurs en alpha, plus leur graphe transitif : la plus lourde charge d’épinglage et de vérification de toutes les options.
    Possibilité de reverser en amont : les parcours pourraient ensuite devenir une variante dans player-reference-examples. Kotlin 2.3 / AGP 8.11 / JDK 21 ; sa logique de compilation et sa génération de code (ig-codegen) sont à auditer par nos soins.
      Une grande partie du modèle (authentification, synchronisation, registres du personnel) est sans rapport avec les parcours et constitue du bruit dans un démonstrateur.

    Option B — Application Compose Multiplatform propre et légère sur les bibliothèques KMP d’OHS (recommandée)

    Une petite application Compose Multiplatform (Android d’abord, cible web en parallèle) écrite pour les quatre parcours, utilisant les mêmes bibliothèques de base que le Player — fhir-model-r4, fhir-engine (stockage sur l’appareil), fhir-data-capture (questionnaires SDC pour l’enregistrement de J2 et l’importation de J3), fhir-workflow (PlanDefinition/$apply pour le calendrier de J3) — et, en option, dev.ohs.player:client pour des vues pilotées par la configuration.

    Avantages Inconvénients
    Mêmes bibliothèques OHS actuelles que le Player : elle montre donc la pile vers laquelle tend l’OHS Foundation, sans la couche authentification/synchronisation/injection de dépendances du modèle. Ce n’est pas l’application Player elle-même ; les écrans sont les nôtres.
    Hors ligne et sans serveur dès le départ ; la tâche d’intégration continue sur émulateur peut piloter les parcours. Les bibliothèques KMP sont en alpha : les ruptures d’API entre versions alpha sont à absorber par nos soins.
    L’ensemble des dépendances correspond à peu près au graphe propre des bibliothèques (Compose MP, client Ktor, Room3/SQLite, kotlinx) — encore conséquent, mais chaque ajout est choisi et répertorié dans docs/dependencies.md. fhir-workflow ne prend pas encore en charge le CQL : les règles de calendrier de J3 doivent être exprimées sous forme de conditions d’applicabilité PlanDefinition en FHIRPath (suffisant pour un calendrier de dose à la naissance ; le CQL de vaccination des lignes directrices SMART de l’OMS attendrait).
    Structure le code de sorte que les écrans des parcours puissent ensuite être proposés à player-reference-examples comme variante du Player.  

    Option C — Android uniquement, sur android-fhir (première génération)

    Une application Android simple sur com.google.android.fhir Engine + SDC (+ Workflow).

    Avantages Inconvénients
    Mature, éprouvée en production (OpenSRP, EmCare) ; la plus grande partie de la documentation et des exemples. En maintenance ; ce n’est pas la direction que prend OHS ; Android uniquement (pas de web).
    La bibliothèque Workflow exécute du CQL aujourd’hui (contenu des lignes directrices SMART de l’OMS). Workflow entraîne HAPI FHIR + le moteur CQL : un graphe de dépendances très volumineux et lourd en JVM.
      Artefacts Google Maven ; la politique réseau de la session bloque actuellement dl.google.com (nécessaire pour ceci et pour AGP/AndroidX dans toutes les options).

    Option D — Web d’abord, sans application Android

    Une page statique sur gh-pages exécutant J1–J4 dans le navigateur avec la bibliothèque Rust/wasm (ou une future version navigateur de hcert-core), plus uniquement le module de test Android pour STT-GEN-004.

    Avantages Inconvénients
    La plus petite : presque aucune dépendance ; la plus facile à montrer à quiconque dispose d’un lien. Pas OHS ; ne montre pas la bibliothèque Kotlin dans une application OHS, ce qui est l’objectif déclaré.
    La bibliothèque Rust/wasm s’exécute déjà dans le navigateur. La bibliothèque Kotlin sur Android n’est exercée que par des tests, et non par un parcours.

    4. Recommandation

    Option B, par étapes :

    1. Module de test Android pour STT-GEN-004 d’abord (indépendant de ce choix).
    2. L’application B, cible Android, hors ligne, J1–J4, sur le moteur dev.ohs.fhir + la saisie de données + workflow.
    3. La cible web de la même application dès que hcert-core disposera d’une cible navigateur (à demander dans smart-trust-tools) — ou, en attendant, les étapes QR des parcours sur le web au moyen de la bibliothèque Rust/wasm.
    4. Plus tard, proposer les parcours à l’OHS Foundation en tant que variante player-reference-examples (décision du propriétaire ; jamais poussé depuis ce dépôt).

    Si être l’OHS Player importe davantage que le nombre de dépendances et une démonstration hors ligne, choisir A : le plan est le même, l’étape 2 partant du modèle et ajoutant d’abord le mode hors ligne.

    5. Ce que toute option exige de l’environnement

    • dl.google.com (Google Maven : AGP, AndroidX, le SDK Android) est bloqué par la politique réseau de cette session. Il est nécessaire pour écrire les métadonnées de vérification Gradle de toute compilation Android. Les exécuteurs de GitHub peuvent y accéder, de sorte que l’intégration continue n’est pas affectée ; les compilations locales ici le sont.
