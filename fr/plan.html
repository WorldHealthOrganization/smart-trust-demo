    Étapes

    1. Plan et squelette (cette PR)

    README (y compris la note sur l’amont smart-trust-phw), AGENTS.md, ce plan, la proposition sur la plateforme de l’application, les directives du propriétaire dans memory/, le registre des dépendances, et une tâche d’intégration continue qui vérifie que chaque GitHub Action est épinglée par SHA de commit et que chaque fichier JSON s’analyse correctement.

    2. Les parcours comme contenu cat-harness

    • (fait) Déclaration smart-trust-demo.json et index.config.json épinglant les couches du harnais que smart-trust-tools épingle (fhir-harness et en dessous), ainsi que smart-trust-tools lui-même, afin que les identifiants req: soient résolus ; index.lock.json.
    • scenarios/ : les acteurs (en réutilisant ceux de smart-trust-tools : titulaire du VHL, partageur, destinataire, participant au réseau de confiance), les rôles qui jouent les couloirs, et les personas : la mère et le nouveau-né (l’exemple de l’IG pour J1), l’infirmière du centre de santé de J1, le CHW (J2), le prestataire du centre de santé du pays de résidence (J3), le portail national et le destinataire à la frontière ou au centre de santé à l’étranger (J4).
    • processes/content/ : un BPMN par parcours (fait à l’étape 2a ; listes de contrôle et montage du harnais à l’étape 2b) (J1 émission, J2 repérage et orientation par le CHW, J3 vérification, importation et calendrier, J4.0 émission du VHL vers un téléphone partagé, J4.1 récupération du VHL au point de soins), des couloirs nommant des rôles, des tâches nommant des skills de smart-trust-tools ; listes de contrôle générées.
    • User scenarios: one per journey, each step tracing to req: nodes (e.g. J2 → STT-VER-011, J3 → STT-VER-001…, J4 → the VHL requirements).
    • Des beans pour les lacunes relevées en chemin (dans ce dépôt, ou marquées pour l’amont : smart-trust-tools, smart-trust ou smart-trust-phw).

    2c. DAK L2 et IG FHIR L3

    Les parcours sous forme de DAK des lignes directrices SMART de l’OMS et d’IG FHIR, structurés comme litlfred/smart-immunizations (sushi-config.yaml, ig.ini, le DAK dans index.config.json (contentTypes.dak), input/). Le contenu L2 est généré à partir des sources du harnais par tools/ig-gen/ig_gen.py : les rôles deviennent des ActorDefinition, le BPMN est copié dans input/business-processes/, les récits et les scénarios deviennent des pages. L’intégration continue vérifie que les fichiers générés sont à jour et que SUSHI compile sans erreur. Ensuite : publier l’IG sur gh-pages et ajouter des ressources d’exemple par parcours (bean IG-01).

    3. La bibliothèque HCERT à un commit épinglé

    lib/hcert/ : un script et un câblage Gradle qui extrait smart-trust-tools à un SHA épinglé, compile hcert-api et hcert-core (JVM) avec le Gradle et le verification-metadata.xml propres à ce dépôt, et copie les jars dans lib/hcert/build/libs/, en échouant si le sha256 d’un jar diffère de celui enregistré dans lib/hcert/hcert.lock.json (la compilation est reproductible). L’application et les tests Android dépendent de ces fichiers. Mettre à jour la bibliothèque consiste en un commit dans le fichier de verrouillage plus build.py --update.

    4. Test sur émulateur Android de la bibliothèque (STT-GEN-004)

    (En cours : android-test/ et .github/workflows/android.yml. Les métadonnées de vérification Gradle sont écrites sur l’exécuteur de GitHub, car cette session ne peut pas accéder à Google Maven.)

    android-test/ : un module de bibliothèque Android dont les tests instrumentés s’exécutent sur un émulateur en intégration continue (niveaux d’API Android à choisir : un actuel, un suffisamment ancien pour compter dans les centres de santé, par exemple 26 et 35) :

    • vérifier l’exemple du §12 de l’IG par rapport au document DID du DSC de XXR (la liste de confiance DEV), avec les fournisseurs de la plateforme Android ;
    • readUnverified du même code QR (J2) ;
    • émettre avec une clé Android Keystore (préparation → signature Keystore → finalisation) et vérifier, en ES256, et en PS256 lorsque la plateforme le propose ;
    • VHL : construire et lire un vhlink:/, déchiffrer la fixture JWE.

    Les résultats sont communiqués à smart-trust-tools comme éléments de preuve pour STT-GEN-004 (et sous forme de beans dans ce dernier pour tout ce qu’Android refuse, par exemple des noms d’algorithmes). Les artefacts Google Maven (AGP, AndroidX test) sont épinglés avec leur sha256 comme tous les autres. La tâche sur émulateur utilise une action épinglée par SHA et ne met en cache aucun artefact non vérifié.

    5. L’application

    (Commencé : app/, la lecture hors ligne de J2, ainsi que la vérification et l’importation par J3 des DVC du guide sur Android, workflow app.yml. Un DVC vérifié devient un Immunization FHIR R4 avec sa Provenance (dev.ohs.fhir:fhir-model-r4) ; un DVC non vérifié n’est pas importé. Ensuite : le calendrier de J3, puis l’émission de J1.)

    Sur la base que le propriétaire choisit à partir de la proposition (recommandée : une application Compose Multiplatform légère sur les bibliothèques KMP d’OHS, Android d’abord) :

    • J1 : le centre de santé émet le DVC du nouveau-né (clé de test intégrée tenant lieu du DSC du centre, ou le Keystore), imprime ou affiche le code QR.
    • J2 : le CHW lit le code QR papier hors ligne (readUnverified), enregistre le nourrisson (questionnaire SDC), crée une orientation (ServiceRequest).
    • J3 : le centre de santé vérifie par rapport à la liste de confiance DEV intégrée, importe les Immunization dans le moteur FHIR de l’appareil, évalue le calendrier (PlanDefinition/$apply), affiche les prochaines doses.
    • J4 : le portail émet des codes QR VHL par membre vers le téléphone partagé ; un destinataire récupère le manifeste (ITI-YY5) auprès d’un partageur de test local et le déchiffre.

    Un test d’interface utilisateur sur émulateur pilote les quatre parcours de bout en bout.

    6. Web et publication

    La cible web (dès que hcert-core s’exécutera dans un navigateur, ou au moyen de la bibliothèque Rust/wasm entre-temps), et le site gh-pages (publié par un agent) : les parcours, les visionneuses BPMN, les personas et les éléments de preuve des tests.

    Points en suspens

    • Réseau : cette session ne peut pas accéder à dl.google.com (Google Maven, le SDK Android). Les étapes 4–5 en ont besoin localement pour écrire les métadonnées de vérification ; le propriétaire peut l’autoriser dans les paramètres réseau de l’environnement.
    • Version navigateur de hcert-core (pour la cible web) : à soulever dans smart-trust-tools.
    • Noms d’algorithmes Android : le code JVM de hcert-core demande RSASSA-PSS, que les fournisseurs d’Android pourraient ne pas proposer sous ce nom ; l’étape 4 le montrera.
