    状态：已于 2026-10-23 决定：选项 B，分阶段进行，同时 Web 端暂用 Rust/wasm 库（memory/dir-app-platform.md）。调研于 2026-10-23。问题：J1–J4 应用应基于什么构建，才能在最新、最 Kotlin 原生的 Open Health Stack 上，于 Android（理想情况下还包括 Web）运行 Kotlin HCERT 库？

    1. Open Health Stack 现状

    Open Health Stack（OHS）最初是由 Google 主导的一组组件，现已成为 OHS Software Foundation，一个隶属 Linux Foundation 的社区项目，WHO 于 2026 年 7 月加入。其代码位于 github.com/ohs-foundation（28 个仓库）。客户端库有两代：

    代际 库 平台 分发 状态
    android-fhir（先行） com.google.android.fhir:engine，data-capture（SDC），workflow，knowledge 仅 Android Google Maven “维护中”；最近一次提交在 2026 年 2–3 月。Workflow 运行 CQL（基于 HAPI，较重）。
    Kotlin Multiplatform（当前） dev.ohs.fhir:fhir-model-r4 1.0.0-rc03，fhir-path-r4，fhir-engine 2.0.0-alpha04，fhir-data-capture 2.0.0-alpha04，fhir-workflow 2.0.0-alpha01；dev.ohs.player:client 1.0.0-alpha03 Android、桌面 JVM、iOS、Web（wasmJs，部分支持 JS） Maven Central 活跃（本周有提交）；alpha 版 API。Workflow 支持 PlanDefinition/$apply；CQL “仍有待推出”。

    在 KMP 这一代之上是 OHS Player，基金会将其描述为跨技术栈的参考工具包，“是参考，而非产品”：

    • player-reference：客户端，一个基于 Compose Multiplatform 的 GitHub 模板应用（Android、iOS、桌面、Web 共用一棵代码树）。界面由配置驱动（在构建时编译的 SQL-on-FHIR ViewDefinition），数据录入由 SDC 问卷驱动。它启动时显示 OIDC 登录，并在与 FHIR 服务器首次同步完成前阻塞；没有内置数据模式。
    • player-client：其背后的库（配置驱动的 FHIR 视图），可单独使用。
    • ohs-player-reference-web-portal：一个用于卫生人力层级（用户、访问权限）的 TypeScript 管理门户。不是临床 Web 应用；与 J1–J4 无关。
    • ohs-player-reference-backend，-infrastructure：后端与部署（FHIR 网关、数据管道）。
    • player-reference-examples：参考应用的变体（目前为空）。日后向上游提供这些旅程的自然之处——这是 OHS Foundation 的仓库，因此只能以提案方式进行，绝不从这里直接提交。

    因此，最新且最 Kotlin 原生的选择是 KMP 这一代，无论是否使用 Player 模板。

    2. 每个选项都必须满足的约束

    1. HCERT 库的 Android 模拟器测试（STT-GEN-004）必须在 CI 中、在包含平台加密功能的 Android 运行时上运行。这与应用无关：它是一个只依赖 HCERT jar 的小型 Android 测试模块（计划第 4 步）。它可以在应用决策之前落地。
    2. 离线且无服务器的演示。J2 按定义就是离线的，而 CI 无法以低成本为模拟器运行搭建 OIDC 提供方和 FHIR 服务器。应用需要内置数据模式。
    3. 供应链。每个构件都以 sha256 固定版本，发布时间 ≥ 14 天，不运行安装脚本。依赖越少越好。
    4. HCERT 库以 JVM jar 的形式来自固定的 smart-trust-tools 提交（所有者的选择）。在 Android 上，JVM jar 可直接使用。在 Web 上目前还不行：hcert-core 的 Kotlin/JS 目标使用 node:crypto 和 node:zlib，因此只能在 Node 上运行，不能在浏览器中运行，而且没有 wasmJs 目标。任何 Web 前端都需要以下之一：hcert-core 中的浏览器目标（WebCrypto，CompressionStream）、smart-trust-tools 中的库修改，或者 Rust/wasm 库——后者已经可以在浏览器中使用 WebCrypto 密钥运行。

    3. 选项

    选项 A——派生（fork）OHS Player 参考应用

    从 player-reference 模板创建应用；添加离线演示模式（内置 FHIR bundle，无需登录）、J1–J4 界面和 HCERT 调用。

    优点 缺点
    它就是 OHS Player：最明显“OHS”的成果，也最接近 OHS 实施者的起点。 启动需要 OIDC 提供方和 FHIR 服务器；离线模式需要我们自己编写，并不断与每周都在变化的模板合并。
    Android、iOS、桌面和 Web 共用一棵代码树；配置驱动的界面；用于登记（J2）和导入（J3）的 SDC 问卷已接好。 其目录中约有 57 个库和 8 个插件（Koin、Ktor CIO/Darwin、Kermit、ksafe、kotlinpoet、BigNum、Compose adaptive……），其中若干为 alpha 版，再加上它们的传递依赖图：在所有选项中固定版本与验证的负担最重。
    可上游化：旅程日后可以成为 player-reference-examples 中的一个变体。 Kotlin 2.3 / AGP 8.11 / JDK 21；其构建逻辑和代码生成（ig-codegen）需要我们自行审计。
      模板的大部分内容（认证、同步、卫生人力登记）与旅程无关，在演示程序中只是干扰。

    选项 B——基于 OHS KMP 库自建精简的 Compose Multiplatform 应用（推荐）

    一个为四段旅程编写的小型 Compose Multiplatform 应用（Android 优先，同时提供 Web 目标），使用与 Player 相同的基础库——fhir-model-r4、fhir-engine（设备端存储）、fhir-data-capture（用于 J2 登记和 J3 导入的 SDC 问卷）、fhir-workflow（用于 J3 接种计划的 PlanDefinition/$apply）——并可选用 dev.ohs.player:client 实现配置驱动的视图。

    优点 缺点
    与 Player 相同的最新 OHS 库，因此能展示 OHS Foundation 正在构建的技术栈，而没有模板的认证/同步/依赖注入（DI）层。 不是 Player 应用本身；界面由我们编写。
    从一开始就离线且无服务器；模拟器 CI 作业可以驱动这些旅程。 KMP 库为 alpha 版：各 alpha 版本之间的 API 破坏性变更需要我们自行消化。
    依赖集大致就是这些库自身的依赖图（Compose MP、Ktor client、Room3/SQLite、kotlinx）——仍然不小，但每一项新增都是经过挑选并列入 docs/dependencies.md 的。 fhir-workflow 尚无 CQL：J3 的接种计划规则必须以 FHIRPath 编写的 PlanDefinition 适用性条件来表达（对出生剂次接种计划足够；WHO SMART 免疫接种 CQL 需要等待）。
    使代码结构便于日后将旅程界面作为 Player 变体提供给 player-reference-examples。  

    选项 C——仅 Android，基于 android-fhir（先行）

    基于 com.google.android.fhir Engine + SDC（+ Workflow）的普通 Android 应用。

    优点 缺点
    成熟，经过生产验证（OpenSRP、EmCare）；文档和示例最多。 处于维护状态；不是 OHS 的发展方向；仅 Android（无 Web）。
    Workflow 库现已可运行 CQL（WHO SMART 指南内容）。 Workflow 会引入 HAPI FHIR + CQL 引擎：一个非常庞大、以 JVM 为主的依赖图。
      Google Maven 构件；本会话的网络策略目前阻止了 dl.google.com（本选项以及每个选项中的 AGP/AndroidX 都需要它）。

    选项 D——Web 优先，无 Android 应用

    gh-pages 上的一个静态页面，在浏览器中用 Rust/wasm 库（或将来 hcert-core 的浏览器构建）运行 J1–J4，另外只有用于 STT-GEN-004 的 Android 测试模块。

    优点 缺点
    最小：几乎没有依赖；最容易通过一个链接展示给任何人。 不是 OHS；无法展示 OHS 应用中的 Kotlin 库，而这正是既定目标。
    Rust/wasm 库已经可以在浏览器中运行。 Android 上的 Kotlin 库只通过测试来运行，而不是通过旅程。

    4. 建议

    选项 B，分阶段：

    1. 首先完成用于 STT-GEN-004 的 Android 测试模块（与本选择无关）。
    2. B 应用，Android 目标，离线，J1–J4，基于 dev.ohs.fhir 引擎 + 数据采集 + workflow。
    3. 一旦 hcert-core 有了浏览器目标（将在 smart-trust-tools 中提出请求），就提供同一应用的 Web 目标——或者在此期间，通过 Rust/wasm 库在 Web 上实现旅程中的 QR 步骤。
    4. 之后，以 player-reference-examples 变体的形式向 OHS Foundation 提议这些旅程（由所有者决定；绝不从这里推送）。

    如果成为 OHS Player 比依赖数量和离线演示更重要，就选择 A：计划相同，只是第 2 步改为从模板开始，并首先添加离线模式。

    5. 任何选项对环境的要求

    • dl.google.com（Google Maven：AGP、AndroidX、Android SDK）被本会话的网络策略阻止。为任何 Android 构建编写 Gradle 验证元数据都需要它。GitHub 的运行器可以访问它，因此 CI 不受影响；但这里的本地构建受影响。
