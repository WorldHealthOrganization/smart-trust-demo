    J4.1

    Taifafeki 的一位医生看到完整的接种史

    回到一切开始的地方，Anan 医生扫描链接，听取通行码，看到 Somsak 完整的第一年——而 Onesa 会被告知是谁查看了记录。

    T0 + 12 months · Kesaro paediatric clinic · Clinic viewer (scan link + passcode) · told through DA Dr. Anan

    回到故事开始的地方，Anan 医生（一位儿科医生）在凯萨罗的一家儿科诊所为 Somsak 看诊。Bounmy 在手机上出示 QR 码并说出通行码。诊所查看器和 Onesa 网关分五步进行：

    1. 查看器针对其信任列表副本中 B 国的 DSC 验证该 HCERT。
    2. 它通过 ITI-YY5 请求清单，并使用 HTTP 消息签名（HTTP Message Signatures）进行签名（STT-VHL-005、STT-VHL-006、STT-VHL-008）。
    3. Onesa 网关检查通行码、有效期和同意，返回清单，并在本国记录此次访问（TrustDemoJ41Access）。
    4. 查看器解密 IPS 和 DVC（STT-VHL-007）（TrustDemoJ41Received）。
    5. 它将这些内容展示给 Anan 医生：自出生以来的每一剂次，仅查看，从不复制。

    错误的通行码会被拒绝，且该尝试仍会记录在 Onesa（TrustDemoJ41WrongPasscode）。如果 HCERT 未通过验证（例如，缓存列表中缺少 B 国的 DSC），则无法进行数字验证。诊所会指明失败的步骤和原因（STT-VER-008），不再访问该 VHL，Anan 医生会像对待纸质记录一样对待家人能够出示的任何资料。

    本步骤之前（1）
    DID 文档已加载

    前提条件（与 J3 相同）：DID 文档已加载。诊所查看器的信任存储是 GDHCN 信任列表的缓存副本，其中包括 B 国 DSC 的 DID 文档（STT-TRU-001、STT-TRU-002、STT-TRU-005）。该诊所每晚或每小时刷新一次，而离线的 J3 诊所大约每周刷新一次。验证时无需联网：验证读取的是缓存，从不获取列表。在上次刷新之后发布的 DSC 无法通过信任列表检查（STT-VER-006），并会注明这一原因。

    如果……

    • 输入了错误的通行码。访问被拒绝，而该尝试仍会记录回 Onesa。

    尚未规定

    • 尚无协议规定 Onesa 由谁阅读访问日志，以及多久阅读一次。

    政策要点。跨境的连续照护：每个国家保存自己的记录，没有国际患者登记系统，也没有供应商锁定。区域层面约定的是数据模型和信任列表，而不是数据的共享副本。

    底层技术

    标准查看器从 Onesa 获取记录，在内存中解密，并在本国留下审计记录。两国之间没有共享数据库也能实现跨境照护。

    使用的构建模块

    工具与应用
    • VHL 查看器系统Taifafeki扫描 QR 码，接收通行码，显示 IPS
      它是什么

      一款网页或平板电脑应用，扫描 VHL QR 码，接收通行码，获取记录并显示。

      意义何在：Taifafeki 的诊所无需在 Onesa 的系统中拥有账户。任何遵循 VHL 标准的查看器都可以使用。

      IHE ITI VHL（接收方）

    • Info Gateway（授权）工具国际依据通行码和同意授权请求，发布数据，写入 AuditEvent
      它是什么

      位于国家 FHIR 服务器前端的授权（AuthZ）层。它检查调用方从身份提供方获得的访问令牌，对每个请求应用访问规则（角色、机构、家庭、同意），并记录每次访问。

      意义何在：从 CHW 手机到 Taifafeki 诊所查看器，每个应用都通过同一个入口。Onesa 将记录保存在本国，并决定谁可以读取或写入哪些内容，包括来自境外的请求。

      OHS FHIR Info Gateway

    • FHIR Data Pipes工具国际将 AuditEvent 输入卫生部的跨境访问仪表板，使异常访问一目了然
      它是什么

      开源管道，将国家服务器中的 FHIR 数据（包括 Provenance 和 AuditEvent）复制到可供分析的表中，用于报告和仪表板。

      意义何在：卫生部看到的是模式，而不仅仅是单条记录：有多少外国证书经过了验证、记录在境外被打开的频率，以及任何异常访问。

      OHS FHIR Data Pipes

    信任与交换
    • 可验证健康链接标准国际已获取清单；已使用解密密钥
      它是什么

      一个已签名的 QR 码，包含链接和解密密钥，而不是数据本身。只有在使用链接时，才会从记录所在地获取记录。

      意义何在：在家人选择的人打开之前，数据一直留在本国。仅凭 QR 码无法获知任何内容。

      IHE ITI 可验证健康链接

    • 审计日志标准国际在 Onesa 记录的 AuditEvent
      它是什么

      关于谁在何时访问了哪些数据以及结果如何的标准记录。

      意义何在：每一次跨境查看都会在本国记录日志，这有助于问责和通知家人。

      IHE BALP · FHIR AuditEvent · 访问日志条目（IG）

    数据标准
    • IPS标准国际为 Taifafeki 临床医生呈现
      它是什么

      一种标准的最小健康摘要（免疫接种、过敏、用药、问题），专为跨境照护而设计。

      意义何在：Taifafeki 医生得到的是一份他们懂得如何阅读、格式可预期的摘要，而不是另一个国家记录的堆砌。

    涉及的要求

    • STT-VHL-005 ITI-YY5 清单请求
      陈述

      库应根据 VHL 载荷构建 ITI-YY5 检索清单请求：POST 到 <base>/List/_search（接受 List?... 或 List/_search?... 两种形式的清单 URL），Content-Type 为 application/x-www-form-urlencoded，请求体包含清单 URL 的搜索参数（_id、code、status 和 patient.identifier 为必需；_include=List:item 为可选），以及 recipient（必需）、passcode（当且仅当载荷的 flag 含 P 时必需）和 embeddedLengthMax（可选）。对于 URL 缺少必需参数的载荷，应予以拒绝。发送请求由宿主负责。

    • STT-VHL-006 ITI-YY5 清单响应
      陈述

      库应读取 ITI-YY5 响应，即一个 FHIR searchset Bundle：其中包含 search.mode 为 match 的 List，以及在使用了“包含 DocumentReference”选项时 search.mode 为 include 的 DocumentReference。对于每个文档，应返回附件 URL 和解密后的内容类型（attachment.contentType）；对于其 DocumentReference 未被包含的 List 条目，应返回引用，供宿主读取。

    • STT-VHL-008 接收方认证：HTTP 消息签名（HTTP Message Signatures）
      陈述

      对于 ITI-YY5 的 HTTP 消息签名（HTTP Message Signatures）选项，库应计算 Content-Digest（RFC 9530，sha-256，结构化字段字节序列），以及基于 @method、@path、@authority、content-type 和 content-digest 并带有 created、keyid 和 alg 参数的 RFC 9421 签名基，返回这些字节供宿主使用接收方的密钥签名，并根据结果组装 Signature-Input 和 Signature 头部。对于 ecdsa-p256-sha256，签名应为 64 字节的 r||s；DER 签名应予以转换。

    • STT-VHL-007 文档加密：JWE dir / A256GCM
      陈述

      文档二进制内容应按照 SMART Health Links，以 JWE 紧凑序列化（RFC 7516）进行加密和解密，使用 alg dir 和 enc A256GCM（RFC 7518），以 VHL 密钥作为内容密钥，并以受保护头部作为附加认证数据。解密应拒绝任何其他 alg 或 enc，应接受 zip DEF，并应在标签错误时失败。加密应将 cty 设置为文档的内容类型。

    • STT-VER-008 类型化的验证结果与失败分类
      陈述

      证书验证失败时，应生成 Failed 结果，而不是异常或崩溃（panic）。Failed 结果应指明失败的步骤，并给出一个原因，该原因取自两种语言共享的封闭集合：BadPrefix、UnsupportedContextVersion、Base45Invalid、InflateFailed、LimitExceeded、CoseMalformed、HeaderInvalid、UnsupportedAlgorithm、KidNotFound、SignatureInvalid、KeyUsageMismatch、Expired、NotYetValid、HcertMissing、MultipleSubclaims、PayloadInvalid。异常或错误应仅用于编程错误和基础设施故障。
