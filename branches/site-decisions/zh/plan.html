    步骤

    1. 计划与骨架（本 PR）

    README（包括 smart-trust-phw 上游说明）、AGENTS.md、本计划、app-platform 提案、memory/ 中的所有者指令、依赖登记册，以及一个 CI 作业，用于检查每个 GitHub Action 都按提交 SHA 固定、每个 JSON 文件都能解析。

    2. 作为 cat-harness 内容的旅程

    • （已完成）smart-trust-demo.json 声明和 index.config.json，固定 smart-trust-tools 所固定的工具框架层（fhir-harness 及以下）以及 smart-trust-tools 本身，使 req: id 可以解析；index.lock.json。
    • scenarios/：参与者（复用 smart-trust-tools 的 VHL 持有人、共享方、接收方、信任网络参与方）、扮演泳道的角色，以及人物画像：母亲和新生儿（J1 的 IG 示例）、J1 诊所护士、CHW（J2）、所属诊所医务人员（J3）、国家门户以及国外边境/诊所的接收方（J4）。
    • processes/content/：每段旅程一个 BPMN（已在步骤 2a 完成；检查清单和工具框架挂载在 2b 完成）（J1 签发，J2 CHW 发现与转诊，J3 验证、导入与接种计划，J4.0 向共享手机签发 VHL，J4.1 在医疗服务点获取 VHL），泳道以角色命名，任务以 smart-trust-tools 技能命名；检查清单为生成的。
    • User scenarios: one per journey, each step tracing to req: nodes (e.g. J2 → STT-VER-011, J3 → STT-VER-001…, J4 → the VHL requirements).
    • 为途中发现的缺口创建 bean（在本仓库中，或标记为上游的 smart-trust-tools、smart-trust 或 smart-trust-phw）。

    2c. L2 DAK 与 L3 FHIR IG

    将旅程作为 WHO SMART 指南 DAK 和 FHIR IG，结构仿照 litlfred/smart-immunizations（sushi-config.yaml、ig.ini、位于 index.config.json（contentTypes.dak）中的 DAK、input/）。L2 内容由 tools/ig-gen/ig_gen.py 从工具框架源文件生成：角色成为 ActorDefinition，BPMN 被复制到 input/business-processes/，故事和场景成为页面。CI 检查生成的文件是否为最新，以及 SUSHI 构建是否无错误。然后：在 gh-pages 上发布 IG，并为每段旅程添加示例资源（bean IG-01）。

    3. 固定提交处的 HCERT 库

    lib/hcert/：一个脚本加 Gradle 配置，在固定的 SHA 处检出 smart-trust-tools，用该仓库自己的 Gradle 和 verification-metadata.xml 构建 hcert-api 和 hcert-core（JVM），并将 jar 复制到 lib/hcert/build/libs/；如果某个 jar 的 sha256 与 lib/hcert/hcert.lock.json 中记录的不同，则失败（构建是可复现的）。应用和 Android 测试依赖这些文件。升级库就是在锁文件中提交一次变更，外加 build.py --update。

    4. 库的 Android 模拟器测试（STT-GEN-004）

    （进行中：android-test/ 和 .github/workflows/android.yml。Gradle 验证元数据在 GitHub 的运行器上编写，因为本会话无法访问 Google Maven。）

    android-test/：一个 Android 库模块，其插桩测试在 CI 中的模拟器上运行（Android API 级别待定：一个当前版本，一个足够旧、对诊所有意义的版本，例如 26 和 35）：

    • 在 Android 平台提供程序上，依据 XXR 的 DSC DID 文档（DEV 信任列表）验证 IG 的 §12 示例；
    • 同一 QR 码的 readUnverified（J2）；
    • 使用 Android Keystore 密钥签发（准备 → Keystore 签名 → 完成）并验证，ES256，以及平台支持时的 PS256；
    • VHL：构建并读取一个 vhlink:/，解密 JWE 测试夹具。

    结果作为 STT-GEN-004 的证据反馈给 smart-trust-tools（对于 Android 拒绝的任何内容，例如算法名称，也在那里创建 bean）。Google Maven 构件（AGP、AndroidX test）与其他所有构件一样以 sha256 固定。模拟器作业使用按 SHA 固定的 action，且不缓存任何未经验证的构件。

    5. 应用

    （已开始：app/、J2 的离线读取，以及 J3 在 Android 上对指南中 DVC 的验证和导入，workflow app.yml。经过验证的 DVC 会成为带有其 Provenance（dev.ohs.fhir:fhir-model-r4）的 FHIR R4 Immunization；未经验证的不会被导入。下一步：J3 的接种计划，然后是 J1 的签发。）

    基于所有者从提案中选择的基础（推荐：基于 OHS KMP 库的精简 Compose Multiplatform 应用，Android 优先）：

    • J1：诊所签发新生儿的 DVC（以内置测试密钥代替诊所的 DSC，或使用 Keystore），打印/显示 QR 码。
    • J2：CHW 离线扫描纸质 QR 码（readUnverified），登记婴儿（SDC 问卷），创建转诊（ServiceRequest）。
    • J3：诊所依据内置的 DEV 信任列表进行验证，将 Immunization 导入设备端 FHIR 引擎，评估接种计划（PlanDefinition/$apply），显示下一剂次。
    • J4：门户向共享手机签发每位成员的 VHL QR 码；接收方从本地测试共享方获取清单（ITI-YY5）并解密。

    一个模拟器 UI 测试端到端地驱动这四段旅程。

    6. Web 与发布

    Web 目标（一旦 hcert-core 可在浏览器中运行，或在此期间通过 Rust/wasm 库），以及 gh-pages 站点（由 agent 发布）：旅程、BPMN 查看器、人物画像和测试证据。

    未决事项

    • 网络：本会话无法访问 dl.google.com（Google Maven、Android SDK）。步骤 4–5 需要在本地访问它来编写验证元数据；所有者可以在环境的网络设置中允许它。
    • hcert-core 的浏览器构建（用于 Web 目标）：将在 smart-trust-tools 中提出。
    • Android 算法名称：hcert-core 的 JVM 代码请求 RSASSA-PSS，Android 的提供程序可能不以该名称提供；步骤 4 将会揭示。
