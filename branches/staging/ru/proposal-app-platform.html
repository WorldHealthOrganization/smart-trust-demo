Вопрос: на чём строить приложение J1–J4, чтобы оно выполняло библиотеку Kotlin HCERT на Android (и, в идеале, в вебе) на самой новой и наиболее нативной для Kotlin версии Open Health Stack?

    1. Что представляет собой Open Health Stack сегодня

    Open Health Stack (OHS) начинался как набор компонентов под руководством Google, а теперь это OHS Software Foundation — общественный проект под эгидой Linux Foundation, к которому ВОЗ присоединилась в июле 2026 г. Его код находится в github.com/ohs-foundation (28 репозиториев). Существует два поколения клиентских библиотек:

    Поколение Библиотеки Платформы Распространение Состояние
    android-fhir (первое) com.google.android.fhir:engine, data-capture (SDC), workflow, knowledge Только Android Google Maven «Сопровождение»; последний коммит — февраль–март 2026 г. Workflow выполняет CQL (на основе HAPI, тяжеловесно).
    Kotlin Multiplatform (текущее) dev.ohs.fhir:fhir-model-r4 1.0.0-rc03, fhir-path-r4, fhir-engine 2.0.0-alpha04, fhir-data-capture 2.0.0-alpha04, fhir-workflow 2.0.0-alpha01; dev.ohs.player:client 1.0.0-alpha03 Android, настольная JVM, iOS, веб (wasmJs, а для некоторых — JS) Maven Central Активно (коммиты на этой неделе); API в альфа-версии. Workflow поддерживает PlanDefinition/$apply; CQL «ещё впереди».

    Поверх поколения KMP находится OHS Player, который фонд описывает как межстековый эталонный инструментарий, «эталон, а не продукт»:

    • player-reference: клиент, шаблонное приложение GitHub на Compose Multiplatform (Android, iOS, настольная версия и веб из одного дерева исходного кода). Экраны управляются конфигурацией (ViewDefinition SQL-on-FHIR, компилируемые во время сборки), ввод данных — анкетами SDC. Приложение открывается входом через OIDC и блокируется до первой синхронизации с сервером FHIR; режима со встроенными данными нет.
    • player-client: лежащая в его основе библиотека (представления FHIR, управляемые конфигурацией), которую можно использовать самостоятельно.
    • ohs-player-reference-web-portal: портал администрирования на TypeScript для иерархий персонала (пользователи, доступ). Это не клиническое веб-приложение; к J1–J4 не относится.
    • ohs-player-reference-backend, -infrastructure: серверная часть и развёртывание (шлюз FHIR, конвейеры данных).
    • player-reference-examples: варианты эталонного приложения (сейчас пусто). Естественное место, чтобы позднее предложить пути в вышестоящий проект, — это репозиторий OHS Foundation, поэтому только в виде предложения и никогда отсюда.

    Поэтому самым новым и наиболее нативным для Kotlin выбором является поколение KMP — с шаблоном Player или без него.

    2. Ограничения, которым должен удовлетворять каждый вариант

    1. Тест библиотеки HCERT в эмуляторе Android (STT-GEN-004) должен выполняться в CI в среде выполнения Android, включая криптографию платформы. Это не зависит от приложения: это небольшой тестовый модуль Android, зависящий только от jar-файла HCERT (шаг 4 плана). Его можно влить до принятия решения о приложении.
    2. Офлайн-демонстрация без сервера. J2 по определению работает офлайн, а CI не может дёшево развернуть поставщика OIDC и сервер FHIR для прогона в эмуляторе. Приложению нужен режим со встроенными данными.
    3. Цепочка поставок. Каждый артефакт закреплён с sha256, релизы возрастом ≥ 14 дней, без скриптов установки. Чем меньше зависимостей, тем лучше.
    4. Библиотека HCERT берётся из закреплённого коммита smart-trust-tools в виде jar-файла JVM (выбор владельца). На Android jar-файл JVM работает как есть. В вебе — пока нет: цель Kotlin/JS в hcert-core использует node:crypto и node:zlib, поэтому она выполняется в Node, а не в браузере, и цели wasmJs нет. Любому веб-интерфейсу нужна либо браузерная цель в hcert-core (WebCrypto, CompressionStream), либо изменение библиотеки в smart-trust-tools, либо библиотека Rust/wasm, которая уже работает в браузере с ключами WebCrypto.

    3. Варианты

    Вариант A — форк эталонного приложения OHS Player

    Создать приложение из шаблона player-reference; добавить офлайн-режим демонстрации (встроенный пакет FHIR, без входа), экраны J1–J4 и вызовы HCERT.

    Плюсы Минусы
    Это OHS Player: наиболее наглядно «OHS»-результат и ближе всего к тому, с чего начнут внедряющие OHS. Для запуска требуются поставщик OIDC и сервер FHIR; офлайн-режим нам придётся написать самим и постоянно сливать с шаблоном, который меняется еженедельно.
    Android, iOS, настольная версия и веб из одного дерева исходного кода; экраны, управляемые конфигурацией; анкеты SDC для регистрации (J2) и импорта (J3) уже подключены. ~57 библиотек и 8 плагинов в его каталоге (Koin, Ktor CIO/Darwin, Kermit, ksafe, kotlinpoet, BigNum, Compose adaptive …), несколько из них в альфа-версии, плюс их транзитивный граф: наибольшая нагрузка по закреплению и верификации среди всех вариантов.
    Можно передать в вышестоящий проект: пути позднее могут стать вариантом в player-reference-examples. Kotlin 2.3 / AGP 8.11 / JDK 21; его логику сборки и генерацию кода (ig-codegen) проверять нам.
      Значительная часть шаблона (аутентификация, синхронизация, реестры персонала) не связана с путями и является лишним шумом в демонстраторе.

    Вариант B — собственное компактное приложение на Compose Multiplatform на библиотеках OHS KMP (рекомендуется)

    Небольшое приложение на Compose Multiplatform (в первую очередь Android, параллельно веб-цель), написанное для четырёх путей, с использованием тех же базовых библиотек, что и Player, — fhir-model-r4, fhir-engine (хранилище на устройстве), fhir-data-capture (анкеты SDC для регистрации в J2 и импорта в J3), fhir-workflow (PlanDefinition/$apply для графика J3) — и, при необходимости, dev.ohs.player:client для представлений, управляемых конфигурацией.

    Плюсы Минусы
    Те же текущие библиотеки OHS, что и у Player, поэтому приложение демонстрирует стек, к которому движется OHS Foundation, без слоя аутентификации/синхронизации/DI из шаблона. Это не само приложение Player; экраны — наши.
    Офлайн и без сервера с самого начала; задание CI в эмуляторе может прогонять пути. Библиотеки KMP находятся в альфа-версии: несовместимые изменения API между альфа-версиями нам придётся учитывать самим.
    Набор зависимостей примерно совпадает с собственным графом библиотек (Compose MP, клиент Ktor, Room3/SQLite, kotlinx) — всё ещё значительный, но каждое добавление выбирается осознанно и указывается в docs/dependencies.md. В fhir-workflow пока нет CQL: правила графика J3 должны быть выражены как условия применимости PlanDefinition на FHIRPath (этого достаточно для графика дозы при рождении; CQL иммунизации WHO SMART придётся отложить).
    Код организуется так, чтобы экраны путей можно было позднее предложить player-reference-examples в качестве варианта Player.  

    Вариант C — только Android, на android-fhir (первое поколение)

    Обычное приложение Android на com.google.android.fhir Engine + SDC (+ Workflow).

    Плюсы Минусы
    Зрелое, проверенное в производственной эксплуатации (OpenSRP, EmCare); больше всего документации и примеров. В режиме сопровождения; OHS развивается не в этом направлении; только Android (без веба).
    Библиотека Workflow уже сейчас выполняет CQL (содержание руководящих принципов SMART ВОЗ (WHO SMART Guidelines)). Workflow подтягивает HAPI FHIR + движок CQL: очень большой граф зависимостей, тяжёлый для JVM.
      Артефакты Google Maven; сетевая политика сеанса сейчас блокирует dl.google.com (он нужен для этого и для AGP/AndroidX в любом варианте).

    Вариант D — в первую очередь веб, без приложения Android

    Статическая страница на gh-pages, выполняющая J1–J4 в браузере с библиотекой Rust/wasm (или будущей браузерной сборкой hcert-core), плюс только тестовый модуль Android для STT-GEN-004.

    Плюсы Минусы
    Наименьший: почти нет зависимостей; проще всего показать кому угодно по ссылке. Не OHS; не показывает библиотеку Kotlin внутри приложения OHS, что является заявленной целью.
    Библиотека Rust/wasm уже работает в браузере. Библиотека Kotlin на Android проверяется только тестами, а не путём.

    4. Рекомендация

    Вариант B, поэтапно:

    1. Сначала тестовый модуль Android для STT-GEN-004 (не зависит от этого выбора).
    2. Приложение B, цель Android, офлайн, J1–J4, на dev.ohs.fhir engine + data capture + workflow.
    3. Веб-цель того же приложения, когда у hcert-core появится браузерная цель (запросить в smart-trust-tools), — или, тем временем, шаги путей с QR в вебе через библиотеку Rust/wasm.
    4. Позднее предложить пути OHS Foundation в качестве варианта player-reference-examples (на усмотрение владельца; никогда не отправляется отсюда).

    Если быть именно OHS Player важнее, чем число зависимостей и офлайн-демонстрация, следует выбрать A: план тот же, но шаг 2 начинается с шаблона и в первую очередь добавляет офлайн-режим.

    5. Что любому варианту требуется от среды

    • dl.google.com (Google Maven: AGP, AndroidX, Android SDK) заблокирован сетевой политикой этого сеанса. Он нужен для записи метаданных верификации Gradle для любой сборки Android. Раннеры GitHub имеют к нему доступ, поэтому на CI это не влияет; влияет на локальные сборки здесь.
